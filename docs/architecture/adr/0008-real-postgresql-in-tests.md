# ADR-0008: Real PostgreSQL in tests

- **Status:** Accepted
- **Date:** 2026-09-18
- **Deciders:** Backend team

## Context

Flyway owns the schema and Hibernate runs with `ddl-auto=validate`, so an entity
that disagrees with the schema stops the application at startup. That check is
only worth something if the tests run the same migrations against the same
database engine that production uses.

The project also relies on PostgreSQL-specific behaviour: `TIMESTAMPTZ` columns,
`CHECK (username = lower(username))` constraints, `BIGINT GENERATED BY DEFAULT AS
IDENTITY`, a `UUID` column type, hash indexes in the Modulith outbox schema, and
PostGIS later for delivery zones.

Developers run tests on Windows and macOS laptops. At least one developer has no
Docker installation, and CI runs on GitHub Actions runners.

## Problem

What database do tests that start the Spring context run against?

## Options considered

| Option | Pros | Cons |
|--------|------|------|
| H2 or HSQLDB in PostgreSQL compatibility mode | fast; zero setup; in-process | not PostgreSQL: `TIMESTAMPTZ`, identity syntax, hash indexes and PostGIS differ or are missing; migrations need an H2-only variant, so the tested schema is not the real schema; `ddl-auto=validate` then validates against the wrong thing |
| Testcontainers PostgreSQL | the real engine and the real migrations; the standard choice | requires a working Docker daemon on every machine and in CI; fails outright for a developer without Docker; container start adds to every build |
| A PostgreSQL instance each developer installs and maintains | real engine; fast once running | shared mutable state between test runs; version drift between laptops; CI still needs a service container; new-joiner setup grows |
| zonky embedded-postgres: real PostgreSQL binaries started by the JVM | the real engine and the real migrations; no Docker; one instance per test JVM; version pinned in `pom.xml` | binaries are downloaded and unpacked on first run; one more dependency; not the industry default, so it needs explaining |

## Decision

Tests that start the Spring context extend
`src/test/java/com/groceryecom/PostgresIntegrationTest`, which starts one real
embedded PostgreSQL 17 server per test JVM using
`io.zonky.test:embedded-postgres`, and points the datasource at it with
`@DynamicPropertySource`. The production Flyway migrations in
`src/main/resources/db/migration` run against it, so the schema and the SQL are
exercised for real and `ddl-auto=validate` means something.

The PostgreSQL version is pinned by
`embedded-postgres-binaries.version` (17.11.0) in `pom.xml`, matching the
PostgreSQL 17 used in `docker-compose.yml` and in production.

Pure unit tests do not start Spring and do not touch a database: `MoneyTest`,
`JwtTokenProviderTest`, and service tests with Mockito.

`./mvnw verify` runs everything, with no Docker required.

## Reason

The two properties that mattered were "same engine as production" and "runs on
any laptop with a JDK". H2 fails the first, Testcontainers fails the second.
Zonky gets both by starting the same PostgreSQL binaries in-process.

One server per JVM rather than one per test class keeps the cost to a single
startup per build, which is what makes running the real engine affordable in the
default `verify` path instead of behind a profile people never enable.

## Consequences

**Positive**

- Migrations are tested on every build; a broken migration fails CI, not a
  deploy.
- `ddl-auto=validate` catches entity/schema drift in tests.
- PostgreSQL-specific SQL, constraints and types behave as they will in
  production. `AuthFlowIntegrationTest` exercises register, login, refresh and
  change password end to end against real PostgreSQL.
- No Docker requirement, so a new joiner can run the full suite after cloning.

**Negative**

- The first build on a machine downloads and unpacks PostgreSQL binaries.
- Starting a database server adds seconds to every build that loads a context.
- One server per JVM means test classes share a database, so tests must clean up
  their own data rather than assume an empty schema.
- The embedded binaries and PostGIS are separate concerns: the embedded server
  has **no PostGIS extension**, so the first PostGIS migration will need a
  different arrangement for tests.

**Revisit when**

- A migration needs PostGIS, which the embedded binaries do not provide. At that
  point either add a PostGIS-enabled embedded provider or move context tests to
  Testcontainers and accept the Docker requirement.
- Build time from database startup becomes the dominant cost, at which point
  reuse across modules or a shared instance in CI is worth looking at.
