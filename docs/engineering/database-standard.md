# Database standard

PostgreSQL 17 is the only primary datastore
([ADR-0002](../architecture/adr/0002-postgresql-as-primary-database.md)). Redis
is a cache and never the source of truth.

## Flyway owns the schema

- Migrations live in `src/main/resources/db/migration`.
- File name: `V<n>__<module>_<change>.sql`, for example
  `V3__vendor_create_vendors.sql`. The number is the next free integer, the
  module name matches the owning module's package, the change is a short verb
  phrase.
- Hibernate runs with `ddl-auto=validate`. It never creates or alters anything;
  an entity that disagrees with the schema stops startup.
- **Never edit a migration that has run anywhere shared** — not on `main`, not in
  CI, not in production. Flyway checksums it and the next startup fails. Write a
  new migration instead.
- One migration per logical change. Do not bundle three unrelated tables into one
  file.
- Start each file with a comment naming the module and the entity it backs, as
  `V1__identity_create_users.sql` does.

Existing migrations:

| File | Contents |
|------|----------|
| `V1__identity_create_users.sql` | `users` table |
| `V2__platform_create_event_publication.sql` | Spring Modulith outbox table, copied from `spring-modulith-events-jdbc` 2.1.1 `schemas/v2/schema-postgresql.sql` |

`V2` is vendored library SQL. When Spring Modulith is upgraded, compare against
the upstream schema for that version before assuming nothing changed.

## Identifiers

Two identifiers per row, and they have different jobs:

| Column | Type | Where it appears |
|--------|------|------------------|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | inside the database and inside the owning module only |
| `public_id` | `UUID NOT NULL UNIQUE` | URLs, API responses, JWT subjects |

The numeric key keeps indexes and joins compact. The UUID stops anyone counting
or enumerating rows from the outside. `BaseEntity` provides `id`; each entity
declares its own `public_id` and assigns it in `@PrePersist`, as `User` does.

A numeric id in a URL or a response body is a bug.

## Types

| Concept | Column | Java |
|---------|--------|------|
| Money | `BIGINT` minor units **plus** a `CHAR(3)`/`VARCHAR(3)` currency code | `shared.money.Money` |
| Point in time | `TIMESTAMPTZ` | `Instant`, UTC |
| Enumerated value | `VARCHAR` with a `CHECK` constraint | `@Enumerated(EnumType.STRING)` plus `@JdbcTypeCode(SqlTypes.VARCHAR)` |
| Flag | `BOOLEAN NOT NULL DEFAULT` | `Boolean` on the entity |
| Public identifier | `UUID` | `UUID` |

Never `NUMERIC`, `REAL` or `DOUBLE PRECISION` for money. Never a native
PostgreSQL enum type — adding a value to one is a schema change; a `VARCHAR` plus
`CHECK` is a one-line migration.

Never `TIMESTAMP` without a time zone. `spring.jpa.properties.hibernate.jdbc.time_zone=UTC`
is set, and mixing the two silently shifts values.

## Constraints

Put the rule in the database, not only in Java. `V1` shows the intended level:

```sql
CONSTRAINT uk_users_username UNIQUE (username),
CONSTRAINT ck_users_username_lower CHECK (username = lower(username)),
CONSTRAINT ck_users_role CHECK (role IN ('CUSTOMER', 'VENDOR_OWNER', 'VENDOR_STAFF', 'ADMIN'))
```

- Every column that must have a value is `NOT NULL`.
- Every natural key is `UNIQUE`. Application-side "does it exist" checks race;
  the constraint does not.
- Usernames and emails are stored lower-case, guarded by a `CHECK`. The
  application normalises before writing.
- Naming: `pk_`, `uk_`, `fk_`, `ck_`, `idx_`, each followed by the table name and
  the columns.
- Adding a role or a status value means updating the matching `CHECK` in a new
  migration. Forgetting this is a common bug: the enum accepts it, the database
  does not.

## Vendor ownership

Every vendor-owned row carries `vendor_id BIGINT NOT NULL`, and **every index on
such a table starts with `vendor_id`**. A vendor's queries are always scoped to
that vendor, so a leading `vendor_id` is what makes the index usable.

This is a rule for the modules that do not exist yet (`vendor`, `catalog`,
`inventory`, `order`, `payment`, `delivery`). `users` is not vendor-owned.

## History and deletion

- **Orders and payments are never deleted and never updated in place for
  status.** A status change appends a row to a status history table.
- `BaseEntity` provides `is_active` and `is_deleted`; a soft delete sets
  `is_deleted = true`. Every read path must filter on it — `is_deleted` with no
  filter is worse than a hard delete.
- Order items copy name, unit, price and tax at purchase time. A later price or
  name change must not alter what a customer was charged.

## Growth

High-volume tables (`orders`, `order_items`, payment tables, event logs) include
`created_at` in their primary key from the first migration, so they can be
partitioned by month later without rewriting the key. Adding it afterwards means
rebuilding the table.

Only add an index for a query you have. An unused index costs every write. Find the
query that is actually slow with `pg_stat_statements` and read its plan before adding
one: [database operations](../development/database-operations.md#finding-a-slow-query).

## Connections and roles

`DB_POOL_SIZE` (default 20) is **per app instance**. Instance count times pool
size must stay under the PostgreSQL connection limit; 8 instances at 20 is 160,
which fits a typical managed limit (and the 200 the local server is started with).
Raising the pool on a running system without checking the server limit is how
deploys fail.

Two roles, and application code only ever gets the weaker one
([ADR-0013](../architecture/adr/0013-least-privilege-database-roles.md)):

| Role | Used by | May |
|------|---------|-----|
| owner (`grocery`) | Flyway migrations | create, alter and drop |
| runtime (`grocery_app`) | the API | `SELECT`, `INSERT`, `UPDATE`, `DELETE` only |

So the schema can only ever change through a migration, and an injection flaw
cannot drop a table. A table created by hand rather than by a migration is not
usable by the application until it is granted — which is the point.

Statements from a pooled connection are cancelled after 10 seconds
(`statement_timeout`); locks wait at most 3 seconds. Migrations run on their own
Flyway connection, without those limits.

## Transactions and queries

- `@Transactional` on the service method, `readOnly = true` for reads.
- Spring Data repository interfaces are the only persistence port; there are no
  hand-written repository implementations
  ([ADR-0004](../architecture/adr/0004-jpa-entities-as-domain-model.md)).
- Derived query methods first; `@Query` with named parameters when a derived name
  would be unreadable. Never build SQL or JPQL by string concatenation.
- Watch for N+1: a loop that dereferences a lazy association issues a query per
  row. Use a fetch join or a projection.
- `open-in-view` is off, so a lazy association touched outside the transaction
  throws. Load what the response needs inside the service.

## Testing a migration

Tests run the production migrations against a real embedded PostgreSQL 17, so a
broken migration fails the build
([ADR-0008](../architecture/adr/0008-real-postgresql-in-tests.md)).

```bash
./mvnw verify
```

Before pushing a migration, check:

1. `./mvnw verify` passes — the migration applied and `ddl-auto=validate` agreed
   with the entities.
2. The change is backward compatible with the currently deployed version. A
   deploy runs migrations before the old instances are gone, so dropping or
   renaming a column in use breaks the running application. Split it: add the new
   column, ship code that writes both, drop the old one in a later release.
3. The embedded test server has **no PostGIS extension**. A migration that needs
   PostGIS will not pass tests as things stand today; raise it rather than
   skipping the test.

## Local database

`docker compose up -d` starts PostgreSQL (`postgis/postgis:17-3.5`), Redis and
RabbitMQ with the credentials that `application.yml` defaults to. Connect with
`psql -h localhost -U grocery -d grocery_ecom` (password `grocery`).

To start from an empty schema, remove the volume:
`docker compose down -v && docker compose up -d`. That also re-runs
`ops/postgres/init`, which creates the runtime role and `pg_stat_statements`.

Everything operational — roles, migrations, slow queries, backups, and what to do
when a symptom appears — is in
[database operations](../development/database-operations.md).
